# Старт разработки Go без Python-платформы

Минимальный пакет S0/PY00, контракт **0.1.0**, 8 ноября 2026. Go-сервис ещё не реализован. Передать коллеге:

- [ТЗ Go](go-annotation-service-spec.md): бизнес-правила и AC01–AC24.
- [Общий OpenAPI](contracts/annotation-service.openapi.json): единственная копия внутренних DTO, заголовков, примеров ответов/снимка и ошибок.
- [Синтетический manifest](contracts/fixtures/annotation-v0.1/manifest.json), [CreateTask](contracts/fixtures/annotation-v0.1/create-task.json) и три PNG из той же папки.
- [Standalone smoke-клиент](../scripts/annotation_contract_smoke.py), только стандартная библиотека Python 3.

Это узкий стартовый комплект, а не завершение всего PY00: публичные DTO FastAPI и тестовый HTTP-транспорт с тайм-аутами/потерей ответа делаются на стороне платформы отдельно. Новых зависимостей и общей инфраструктуры здесь нет.

## Что можно реализовать независимо

Go владеет заданиями, назначениями, рамками, ревизиями, submit/review, аудитом и неизменяемыми снимками. Python будет владеть пользователями, проектами, доступом, файлами/S3, нормализацией, версиями датасета и экспортом. Frontend отдельно реализует редактор через публичный FastAPI; размеры Canvas не меняют пиксельные координаты.

Go **не скачивает PNG или S3** и не требует настоящих пользователей/проектов Python для этого стенда. Тестовый клиент доверенно передаёт фиксированные ImageContext и схему классов. В manifest есть синтетический project UUID и роли: `1 admin`, `2 manager`, `3 annotator`, `4 reviewer`. Создание и снимок выполняются менеджером, сохранение/отправка аннотатором, приёмка рецензентом; admin зарезервирован для других проверок.

Три RGB PNG имеют размер 640 × 640, реальные SHA-256 и стабильные ImageVersion UUID. В первом прямоугольник `[80,120,300,400]`, во втором `[320,200,640,640]`, третий пустой и явно `negative`. Правая/нижняя границы координат исключительные. Это технические прямоугольники с меткой `horse`, **не изображения лошадей и не эталон качества разметки**. Три независимые синтетические сессии и отсутствие одинаковых байтов дают будущим проверкам разделения маленький тестовый состав; это не реализация алгоритма train/val/test. Сессии остаются метаданными платформы и не добавляются в CreateTask.

Task, task-item, submission, review и snapshot UUID выдаёт Go. Smoke получает task ID из POST, затем сопоставляет task-item по `image_version_id` из GET items; выдуманных фиксированных серверных ID в сценарии нет. Request ID в сохранённом CreateTask — лишь пример: live-клиент заменяет его детерминированным UUID от `--run-id`.

## Проверка комплекта без сервисов

Из корня репозитория:

```sh
python3 scripts/annotation_contract_smoke.py --check-fixtures
python3 scripts/annotation_contract_smoke.py --help
```

Без флагов выполняется та же офлайн-проверка, без сети и записей. Проверяются PNG CRC, исходные пиксели известных прямоугольников/негатива, размеры, SHA-256, сессии, согласованность CreateTask и его схема из общего OpenAPI. Проверка схемы покрывает используемое подмножество CreateTask, не заменяет полноценный OpenAPI-валидатор.

## Что настроить в реализации коллеги

Нужны локальный адрес/порт HTTP, подключение к отдельной тестовой PostgreSQL, схема `annotation`, рабочая роль Go, отдельная роль/команда миграций, служебный Bearer token и HTTP/DB timeouts. Имена переменных, драйвер, способ запуска PostgreSQL и команды запуска/миграций определяет реализация коллеги; готовой команды запуска Go здесь нет. Рабочая роль не получает доступа к Python-таблицам. Требования к неизменяемым записям и правам БД определены в ТЗ. До запуска smoke применить миграции; `/healthz` и `/readyz` реализовать по контракту.

Служебный токен отличается от JWT-секрета платформы. Он задаётся сервису и тестовому клиенту через окружение/средства локального запуска; значения не входят в Git, журнал или вывод. Клиент читает **только** `ANNOTATION_SERVICE_TOKEN` из окружения и не читает `.env`.

Прямой обход шлюза с `X-Actor-ID`/`X-Actor-Role` разрешён только доверенному аутентифицированному тестовому клиенту в локальном стенде. В продукте эти заголовки формирует FastAPI после проверки пользователя и проекта; браузер не получает служебный токен и не задаёт доверенный actor-контекст.

## Smoke после реализации

Задать `ANNOTATION_SERVICE_TOKEN` в окружении тем же значением, что использует Go. Выбрать UUID один раз и сохранить его. Например, следующий UUID годится для одного отдельного запуска в чистом стенде:

```sh
python3 scripts/annotation_contract_smoke.py --run \
  --base-url http://127.0.0.1:8081 \
  --run-id 4fbcb25c-d34f-49c8-a786-5270c3737a65 \
  --state-dir /tmp/annotation-smoke-runs
```

`--run` изменяет только указанный локальный Go. Клиент разрешает HTTP origin `localhost`, `127.0.0.1` или `::1`, отключает прокси и переходы по redirect. Токен и серверные сообщения об ошибках не печатаются. При сетевой ошибке или нарушении проверяемого контракта exit code ненулевой. Чистку созданных заданий клиент не выполняет: API удаления нет, используйте отдельную тестовую БД.

Сценарий: create → items/context → два положительных сохранения и один negative → повтор каждого PUT с тем же request_id и сравнением JSON-результата → stale expected_revision с отдельным ключом и 409 revision_conflict → submit точных ревизий → accept reviewer → snapshot manager → content. Проверяются состав, классы, геометрия, ссылки, количества **3 кадра / 2 рамки / 1 negative**, SHA-256 исходных JSON-байтов и заголовок `X-Content-SHA256`; повтор GET content должен вернуть те же байты. PNG-хеши в снимке сверяются с локальными исходными файлами; PNG не передаются Go.

При неизвестном результате повторить **точно ту же команду**, сохранив UUID, каталог журнала и файлы комплекта. Не запускать два клиента с одним run-id одновременно. Журнал записывает тело до отправки и подтверждённые ответы без токена. Ключи мутаций — UUIDv5 от run-id и имени операции. Создание/сохранения/submit/review/snapshot повторно уходят на сервер с неизменными телами и request_id; начальная task_revision берётся из исходного идемпотентного POST create, а не текущего GET task. Уже подтверждённый 409-пробник при продолжении пропускается, поскольку задание могло перейти в accepted. Остальные ответы повторов должны совпасть с исходными JSON-телами; заголовок трассировки в это сравнение не входит.

После потери журнала нельзя надёжно продолжить завершённый сценарий с прежним run-id: в частности, свежая отрицательная проба уже замороженного задания даст другую ошибку. Для нового независимого сценария использовать новый UUID. После очистки/пересоздания БД также начать с нового UUID и нового журнала.

## Остальная приёмка

Этот smoke не заменяет AC01–AC24 из ТЗ. Коллега дополнительно проверяет миграции и готовность, отсутствие/подмену аутентификации, проектную видимость и роли, начальную ревизию 0, геометрию/дробные координаты/предупреждения, историю и возврат с исправлением, запрет собственной приёмки, повтор ключа с другим телом, настоящие конкурентные операции, rollback/сбой после commit, пагинацию, лимиты, аудит/SQL-права, неизменяемость снимков, нагрузку и восстановление. Полная интеграция через FastAPI, S3 и браузер выполняется позже по PY09, независимо от готовности этого технического старта.
