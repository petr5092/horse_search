# План реализации Python платформы для интеграции с Go сервисом

Дата: **8 ноября 2026 года**. Статус: **план для согласования**. Базовый контракт: **0.1.0**.

Реализовать Python-часть Horse Dataset Studio так, чтобы Go-сервис мог независимо разрабатывать задания и разметку, а платформа обеспечивала достоверные изображения, проектные права и воспроизводимый экспорт. Основания: [ТЗ Go-сервиса](go-annotation-service-spec.md) и [OpenAPI](contracts/annotation-service.openapi.json).

Первый результат интеграции — создать задание из подготовленного изображения через FastAPI, открыть разрешённый кадр и сохранить разметку в Go. Полный результат пилота — получить принятую разметку, зафиксировать версию датасета и построить одинаковые по составу экспорты COCO и YOLO.

**Реализован минимальный Python S1:** проекты и роли, каталог подготовленных
изображений, шлюз 17 операций Go, локальный seed, отдельная конфигурация стенда
и публичный smoke. Запуск и границы фактических проверок описаны в
[инструкции S1](python-s1-start.md). Это части PY01–PY04 и PY06; обработка новых
изображений, worker, версии датасета и экспорт остаются последующими этапами.

## Исходное состояние

В коде уже есть FastAPI, JWT-аутентификация, пользователи с глобальными ролями, SQLAlchemy/Alembic и приватные файлы в S3. Существующий файловый сценарий включает загрузку, проверку SHA-256 и удаление; его изолированные тесты используют SQLite и moto.

Проектов, участников, рабочих изображений, клиента Go, фонового worker и версий датасета пока нет. Приложение вызывает `create_all` при запуске, DAO самостоятельно открывает сессии и делает commit. Compose поднимает MinIO. Новую функциональность нужно строить поверх существующей основы, сохраняя действующие `/auth` и `/files`.

## Границы и решения для пилота

- Python владеет пользователями, проектами, участниками, происхождением изображений, обработкой файлов, S3, версиями датасета, разделением выборок и экспортами.
- Go владеет заданиями, назначениями, документами разметки, ревизиями, отправками, рецензиями и снимками принятой работы. Python не создаёт второй источник состояния этих сущностей и не обращается к таблицам `annotation`.
- Публичная точка входа — FastAPI. Редактор на TypeScript является отдельной задачей; этот план обеспечивает его API и проверку без UI.
- Общая интеграционная среда использует PostgreSQL. У сервисов разные роли БД и миграции; Python Alembic не управляет схемой Go. Рабочие роли отделены от ролей миграций.
- Новые бизнес-сервисы получают сессию извне и управляют транзакцией на уровне операции. Существующий DAO пользователей не переписывается целиком; необходимые изменения выполняются локально.
- Для пилота фоновые задания хранятся в PostgreSQL и исполняются отдельным Python-процессом. Это предлагаемое решение плана: импорт, нормализация и экспорт используют общий механизм jobs с lease и восстановлением. HTTP-процесс не выполняет долгую обработку изображений. Выбор готового брокера можно пересмотреть до PY05, сохраняя доменную модель jobs и интерфейсы.
- Начальный вход — отдельные файлы изображений через существующую загрузку. ZIP, видео, импорт S3 URI и предразметка моделью вынесены в последующие этапы, чтобы сначала проверить ручной сквозной процесс.

## PY00 Общий контракт и примеры

**Готов минимальный комплект S0 для коллеги:** [инструкция](go-service-start.md),
три синтетических PNG с реальными хешами, manifest, запрос CreateTask и
standalone smoke-клиент. Он позволяет начать Go без реализации платформы.
Это выполненная часть PY00; публичные DTO FastAPI и тестовый HTTP-транспорт
остаются в плане и для независимого старта Go не требуются.

**Работы.** Зафиксировать формы публичных запросов FastAPI, преобразование в запросы Go и примеры нового контекста изображения. Внутренний OpenAPI Go остаётся единственной общей копией. Публичные отличия документировать отдельно: создание задания принимает идентификаторы изображений, а контекст редактора содержит ссылку просмотра.

Подготовить небольшие JSON-примеры с согласованными UUID и четырьмя тестовыми ролями, используя примеры OpenAPI. Для нормализации и экспортов создать синтетические изображения с известными размерами и реальными SHA-256; это технические данные, а не эталон качества разметки. Для полной версии нужны как минимум три независимые сессии съёмки и проверенный негативный кадр. Секреты и пользовательская база в примеры не входят.

Тестовый транспорт Go должен поддерживать заранее заданные ответы и ошибки, включая потерю ответа после успешной операции. Он не реализует второй движок заданий и не включается как fallback при недоступности настоящего Go.

**Готовность.** Коллега получает версии контрактов, примеры `ImageContext`, заголовков, принятых снимков и матрицу ошибок. Python-тесты могут воспроизвести создание задания, контекст, 409, тайм-аут и снимок без запуска Go. Изменения контракта согласуются до зависимого кода.

## PY01 Основа приложения и PostgreSQL

**Работы.** Добавить PostgreSQL и роли в локальную интеграционную конфигурацию. Сделать Alembic обязательным способом изменения схемы; убрать `create_all` из штатного запуска после подготовки миграционного пути. Сервис должен явно сообщать о неприменённых миграциях. Проверить upgrade для существующих таблиц пользователей и файлов, не меняя их UUID, владельцев и S3-ключей.

В lifespan создать общий `httpx.AsyncClient` для Go и закрывать его при завершении. В конфигурацию добавить фиксированный внутренний адрес сервиса, отдельный служебный токен, ограничения соединений и connect/read/write/pool timeouts. Для получения снимков предусмотреть отдельные лимиты времени и размера.

Организовать зависимости сессий и транзакции новых модулей, общие ошибки пространства `/api` и ID трассировки. Не держать сессию с открытой транзакцией на время обращения к Go или S3. Структурированные логи не содержат токены, тела разметки и подписанные ссылки. Базовая готовность Python проверяет его БД; отказ Go отражается в операциях разметки, не выключая авторизацию и файлы.

**Готовность.** Миграции воспроизводимы на пустой PostgreSQL и на тестовой базе старой схемы. Существующие файловые тесты проходят; новые проверки транзакций используют PostgreSQL. Рабочая роль Python не имеет доступа к схеме Go. Изменение подключения рабочей базы и перенос существующих данных выполняются отдельным проверяемым шагом после проверки миграций.

## PY02 Проекты и эффективные роли

**Работы.** Добавить проекты `active/archived`, участников и неизменяемые версии схемы классов. Для пилота проект создаёт глобальный администратор и назначает первого менеджера. Менеджер управляет участниками своего проекта. Начальная схема содержит `horse`, размер рабочих изображений — 640 × 640.

Предлагаемая политика: активный глобальный `admin` получает эффективную роль `admin`; для остальных активных пользователей она берётся из `ProjectMember.role` (`manager`, `annotator`, `reviewer`). Глобальная роль неадминистратора и старый claim JWT не подменяют проектную роль. Для скрытого проекта возвращается 404, для видимого, но недопустимого действия — 403. Архивный проект доступен для разрешённого чтения; новые изменения в нём запрещены.

Все пользовательские запросы повторно проверяют активность пользователя и участие в проекте. Перед созданием или переназначением задания проверяются активность, участие и роли обоих назначаемых пользователей. Условия запрета собственной приёмки остаются в Go, где есть история авторства.

**Готовность.** Тесты покрывают два проекта, разные роли одного пользователя, отзыв доступа, деактивацию, архивирование и поддельные actor-заголовки. Значение `X-Actor-Role` однозначно выводится сервером. Отдельно проверяется, что некорректный токен или `sub` не приводят к 500 в новых маршрутах.

## PY03 Клиент Go и шлюз

**Работы.** Реализовать `AnnotationClient` поверх общего HTTPX-клиента, явные DTO контракта и маршруты разрешённых операций. Список берётся из OpenAPI: 17 операций проекта; `/healthz` и `/readyz` Go не превращаются в пользовательские маршруты проекта. Префикс FastAPI `/api/projects/{project_id}/annotation/` преобразуется в `/v1/projects/{project_id}/`.

На входе выполнить проектную авторизацию, удалить поступившие служебные заголовки и сформировать `Authorization` со служебным токеном, `X-Actor-ID`, эффективную роль и валидный `X-Request-ID`. Не пересылать в Go пользовательские Cookie/JWT, произвольные адреса, Host и hop-by-hop заголовки. Идентификатор операции `request_id` не заменяется ID трассировки.

Сохранять статус и смысл ошибок Go, включая 409 и `details`. Сетевой отказ переводить в 502 `upstream_unavailable`, тайм-аут — в 504 `upstream_timeout`. Ответ, нарушающий контракт, не считать успешным. Повторы операций изменения допускаются только с тем же `request_id` и зафиксированным телом; скрытого повтора с новым UUID нет.

Ответ `/snapshots/{id}/content` передавать точными байтами с SHA-256, без JSON parse/re-encode. Для скачивания запросить identity encoding и проверять размер. Остальные ответы проходят проверку DTO; контекст изображения обогащается только в PY06.

**Готовность.** HTTP-тесты проверяют методы/пути, курсоры, actor-заголовки, ошибки, отмену/тайм-аут и неизменность байтов снимка. Нет обращений к SQL Go и нет подмены недоступного сервиса локальными данными. Открытый произвольный HTTP-прокси отсутствует.

## PY04 Данные изображения и сохранность файлов

**Работы.** Добавить `Asset` со ссылкой на готовый `StoredFile` и происхождением: URI источника, лицензия или разрешение использования, сессия съёмки, дополнительные сведения о камере/животных при наличии. Проверять наличие и допустимые значения метаданных; содержательное разрешение на использование не выводится автоматически из одной строки лицензии.

Добавить `ImageVersion` и рецепт обработки. Готовая версия указывает на неизменяемые байты, SHA-256, размеры, параметры преобразования и его версию. До состояния `ready` она не передаётся в Go. Изменение рецепта создаёт новую версию изображения, а не заменяет объект по прежнему идентификатору.

Привязку исходника к проекту разрешить менеджеру/администратору с правом на сам файл. Списки библиотеки исходников и прямой просмотр рабочих изображений для подготовки заданий доступны менеджеру/администратору. Аннотатор и рецензент получают картинку через разрешённый Go-контекст конкретного задания. Существующий доступ к приватным оригиналам не расширяется до всех участников проекта.

Ввести локальные ссылки использования файлов и изображений. Проверка использования в `/files/{id}` выполняется **до** вызова S3 delete, под согласованной с привязкой блокировкой записи файла. FK, который сработает только после удаления из S3, недостаточен. Пока файл связан с Asset, заданием или версией, физическое удаление запрещено. Неопределённый результат создания задания сохраняет ссылки использования.

**Готовность.** Подготовленный тестовый кадр даёт корректный `ImageContext`. Привязка и удаление при гонке не оставляют Asset с отсутствующим объектом. Рабочее изображение нельзя незаметно заменить; другой проект и чужой исходник не получают доступ.

## PY05 Фоновые задания и нормализация

**Работы.** Реализовать таблицу `Job`, отдельный worker, сохранение прогресса и повтор. Состояния — `queued`, `running`, `succeeded`, `failed`; временные ошибки используют ограниченные повторы, постоянные ошибки входных данных завершаются явной причиной. Захват job через PostgreSQL использует короткую транзакцию, `SKIP LOCKED`, lease и уникальный токен попытки; heartbeat и завершение проверяют этот токен. Старый worker после перехвата не может опубликовать результат.

Нормализация: прочитать оригинал и проверить его хеш, проверить декодирование и лимиты изображения, учесть EXIF orientation, перевести в RGB и выполнить letterbox. Цвет полей, фильтр, формат и настройки кодирования фиксируются рецептом. Сохранить исходные размеры после EXIF, реальные размеры масштабированной области, смещения полей и фактические коэффициенты по осям с учётом округления.

Ключи кандидатов S3 и попытка записываются до загрузки. Готовность фиксируется только после записи и проверки объекта. Завершённый job возвращает прежний `ImageVersion`; повтор не перезаписывает готовые байты. Параметры и версии библиотек обработки фиксируются. Уже использованное изображение при обновлении Pillow не пересобирается на месте.

Точные копии выявляются по сохранённым хешам и отражаются в метаданных контроля; исходные записи не удаляются молча. Очистка временных кандидатов не затрагивает готовые или используемые объекты.

**Готовность.** Изображения разных пропорций, EXIF-поворот, RGB/alpha и повреждённые данные покрыты тестами. Выход 640 × 640, пропорции сохранены, геометрическое преобразование проверено на контрольных точках. Падение worker, повтор и позднее завершение старой попытки не меняют опубликованную версию изображения.

## PY06 Создание задания и контекст редактора

**Работы.** Публичный запрос создания задания принимает `request_id`, `title`, `assignee_id`, `reviewer_id`, `label_schema_version` и `image_version_ids`. Python загружает собственную схему классов и метаданные всех готовых изображений проекта. Поля `width`, `height`, `sha256` и определения классов из браузера не принимаются вместо серверных данных.

Перед HTTP-вызовом одной локальной транзакцией сохранить `PlatformOperation`: ключ и хеш публичного запроса, инициатора, проект, точное подготовленное тело Go и ссылки использования изображений. Транзакцию завершить, затем вызывать Go. При успехе сохранить внешний `task_id` и техническую привязку. Состояние задания не копировать как источник истины.

Повтор с тем же ключом использует **тот же подготовленный запрос**, даже если активная схема проекта уже изменилась. Другой публичный запрос с тем же ключом конфликтует. Текущий доступ инициатора проверяется при каждом пользовательском повторе; сохранённая роль не даёт обхода отзыва доступа. Для назначения и создания данные фиксируются при принятии операции; новая операция повторно проверяет текущих участников.

Если Go мог создать задание, но ответ потерян, операция помечается неопределённой. Повтор сохранённой команды разрешает этот исход через идемпотентность Go. Ссылки на изображения не освобождаются по тайм-ауту или произвольной последующей ошибке: после неопределённого исхода требуется подтверждённое разрешение результата. Python не возвращает сохранённый ответ в обход текущих ресурсных прав Go.

В `context` сначала получить разрешённый Go-контекст, затем найти `ImageVersion` в том же проекте, сверить UUID, размеры и SHA-256 и выдать ссылку **просмотра** с корректным MIME. Добавляемые поля — `image_url` и `image_url_expires_at` в корне ответа; Go DTO остаётся без этих полей. Не использовать существующую download-ссылку с `attachment`/`application/octet-stream`. Успешный ответ контекста имеет `Cache-Control: no-store`; URL обновляется повторным запросом без изменения изображения.

**Готовность.** Потерянный ответ после создания не даёт дубликата; повтор после изменения схемы отправляет прежнее тело. Чужой `task_item_id`, несовпадение метаданных и неподготовленный кадр не дают S3-ссылку. Для создания, переназначения и контекста проверены все обязательства платформы из ТЗ Go.

## PY07 Версии датасета и разделение выборок

**Работы.** Добавить создание версии из `submission_ids`, параметров разделения и `request_id`. Сервер принимает операцию и ставит job; пользователь получает `version_id`/`job_id`. Состояния версии — `building`, `ready`, `failed`. Перед межсервисной операцией и публикацией результата worker проверяет текущую активность и полномочия инициатора; отзыв доступа завершает операцию явной ошибкой, а не подменой actor на администратора.

Ключ и точное тело создания снимка в Go сохраняются до вызова. Скачать метаданные и исходные байты снимка, проверить SHA-256, пределы 10 000 кадров/100 000 рамок/64 MiB, количества и соответствие локальным версиям изображений. Сверить проект, размеры, классы и хеши. Для первого пилота одна версия использует совместимую фиксированную схему классов и один целевой размер; несовместимый состав отклоняется явно.

Снимок записать в S3 без преобразования. Зафиксировать метаданные происхождения на момент сборки, состав изображений, схему, версию алгоритма разделения, seed, параметры и контрольные суммы в манифесте. Только после проверки всех артефактов версия переходит в `ready`. После этого её состав и параметры неизменяемы.

Начальная пропорция — 70/15/15. Единица разделения — связанная группа кадров: общая сессия съёмки, известное общее животное или точная копия связывают изображения в одну компоненту. Компонента не делится между выборками. Использовать детерминированный алгоритм с версией и seed; случайный процессный `hash()` не является стабильным идентификатором группы. Сохранять фактические доли: из-за размеров групп они могут отличаться от целевых. Если нельзя получить необходимые непустые train/val/test без утечки, сборка завершается диагностикой, а не случайным разрезанием группы.

**Готовность.** Повтор запроса не создаёт вторую версию. Повреждённый, слишком большой или несовместимый снимок не публикуется. Сбои между Go, S3 и БД восстанавливаются по сохранённой операции. Изменение текущих метаданных Asset не меняет ранее созданную версию. На тестовом наборе группы и известные копии не пересекают выборки.

## PY08 Экспорты и отчёты

**Работы.** Сборка COCO и YOLO читает только `ready`-версию и сохранённые рабочие изображения. Изменения в Go или текущей библиотеке Asset не влияют на сборку. Архивы создаются фоновым job и публикуются только после проверки.

COCO использует пиксельные `[xmin, ymin, width, height]`; YOLO — нормализованные центр и размеры. Маппинг внутренних классов в COCO ID и YOLO index сохраняется в манифесте; для `horse` YOLO index равен 0. Негативные кадры присутствуют в обоих форматах: в COCO без объектов, в YOLO с пустым TXT. Изображения не перекодируются при экспорте.

Порядок изображений, рамок и файлов, генерация внешних ID, точность чисел, JSON/YAML и параметры ZIP фиксируются. Из архива исключаются текущие даты, случайные имена и нестабильные метаданные файлов. Повтор одного экспортного профиля той же версии должен давать одинаковые байты и SHA-256 при закреплённом окружении сборки.

Поставка содержит архив, `manifest.json`, `qa_report.json`, карту датасета и перечень изменений. Для первой версии перечень описывает исходный состав; сравнение со следующей версией добавляет изменённые элементы. Отчёт включает количества кадров/рамок/негативов, распределение по выборкам, проверки координат, групп и контрольных сумм. Создание и скачивание экспортов доступны менеджеру/администратору соответствующего проекта.

**Готовность.** COCO и YOLO содержат одинаковые изображения, объекты и выборки. Конвертация проверена на известных координатах и обратном пересчёте с погрешностью менее 0.5 px. Повторная сборка даёт тот же хеш, неполный архив не выдаётся, изображения в архиве совпадают по SHA-256 с манифестом.

## PY09 Совместная интеграция

**Работы.** Собрать локальные сервисы FastAPI, Python worker, Go, PostgreSQL и MinIO. Go слушает внутренний адрес; служебный токен не попадает в браузер. Для frontend задать явные origin, проверить CORS API и S3 отдельно; для изменяющих запросов с cookie предусмотреть проверку Origin/защиту от CSRF. Запуск и миграции каждого сервиса воспроизводимы отдельно.

Прогнать через публичный FastAPI: регистрация/вход → проект/участники → загрузка → нормализация → задание → разметка → отправка → возврат → исправление → приёмка → версия → оба экспорта. Для полного разделения выборок использовать несколько независимых сессий из PY00. Проверить отключение Go и S3, повтор после потери ответа, отзыв доступа, гонку удаления/привязки и перезапуск worker.

Общий объём — 10 000 кадров и не менее 50 000 рамок. Измерить время подготовки, шлюза и сборки, ошибки, объём артефактов и итоговые хеши; аппаратное окружение приложить к отчёту. Восстановить тестовую копию БД и объектов и проверить повторную сборку контрольного экспорта. Для результата достаточно ручного восстановления по документированной процедуре; автоматизация резервного копирования оформляется отдельной эксплуатационной задачей.

**Готовность.** Полный сценарий и восстановление подтверждены. Ни Go, ни Python не требуют прямого чтения чужих таблиц. Права проверяются через публичный вход, а версии и экспорты остаются воспроизводимыми после новых изменений разметки.

## Точки синхронизации с коллегой

| Точка | Наша готовность | Готовность Go | Совместная проверка |
| --- | --- | --- | --- |
| S0 Контракт | PY00 и примеры | Принятые DTO/заголовки 0.1 | Одинаковые UUID, типы, роли и ошибки |
| S1 Первый кадр | PY01–PY04, PY06; готовый тестовый кадр | Создание задания, context, GET/PUT разметки | Создание и сохранение через FastAPI |
| S2 Проверенная работа | Шлюз отправки/рецензии, PA02–PA07 | Submit, review, история и запрет собственной приёмки | Возврат, исправление, приёмка и конфликт |
| S3 Версия и экспорт | PY05, PY07–PY08 на фиксированном снимке | Снимки принятых отправок | Хеш, состав, разделение и оба формата |
| S4 Пилот | PY09 | AC01–AC24 из ТЗ Go | Полный сценарий, сбои и восстановление |

Коллега не ждёт нашего массового импорта: S1 использует заранее подготовленный технический кадр. Мы не ждём готовой рецензии для разработки экспорта: PY07–PY08 используют сохранённый пример принятого снимка. Корневой Compose и общие Python-файлы меняет наша сторона; коллега владеет `services/annotation-go/` и своей миграционной цепочкой. Изменение общего OpenAPI требует синхронизации обеих сторон.

Первый пакет реализации после согласования плана — PY00–PY03 и минимальный подготовленный набор PY04 для S1. Следующий пакет доводит реальные изображения и восстановление до PY05–PY06. Затем выполняются версии и экспорты PY07–PY08 и совместная приёмка PY09. Конкретные сроки определяются после оценки этих пакетов обоими исполнителями.
